# Parallel on-demand fulfillment

## Rollout (disabled by default)

1. Apply the additive `20261010110000_parallel_lobstr_fulfillment` migration and generate Prisma. Existing jobs keep `parallelConfig = null` and use the original state-wide fulfillment path. No customer balances or historical allocations are changed by this migration.
2. Deploy the web routes and a supervised, persistent SMTP-capable fulfillment worker. Multiple instances can process different parent orders; the existing parent lease prevents two coordinators from driving the same order. Each coordinator manages multiple independent cloud child runs concurrently, rather than separate Node leases per child.
3. Configure `LOBSTR_API_KEY`, existing `LOBSTR_FULFILLMENT_ENABLED=true`, and **an explicitly calibrated** `LOBSTR_ESTIMATED_CREDITS_PER_RESULT`. Provider credits are NOT customer wallet credits. Calibrate against actual billed results, including the scraper's email expansion and enabled enrichment options. A per-result estimate is a conservative admission budget, not a provider-enforced hard spending limit. Monitor actual Lobstr billing.
4. Set `LOBSTR_MAX_CONCURRENT_RUNS` (1–50, default 50), `LOBSTR_BATCH_SIZE` (50–100, default 100), and `LOBSTR_BACKUP_BUDGET_MULTIPLIER` (1–3, default 2). The live balance/slot response can reduce concurrency below these settings. Set the account limit consistently across worker deployments.
5. Only after migration, workers and budgets are ready, enable `LOBSTR_PARALLEL_ENABLED=true`. New shortage orders of 500+ leads use the parallel plan; smaller or older jobs retain the original implementation. Missing/invalid parallel configuration rejects a new shortage order before debiting customer credits. Sufficient database inventory still fulfills immediately without scraper configuration.

## Geographic plan and capacity

- 500 leads normally creates five 100-lead children; 2,500 creates twenty-five children, 5,000 creates fifty, and 10,000 creates one hundred, with at most fifty dispatched concurrently. Partial final shards preserve the exact requested total. Selected states receive balanced targets.
- Each task uses a distinct real five-digit ZIP from the shared `packages/utils/src/territories/us-zip-codes.ts` master registry backed by the MIT-licensed `midwire/free_zipcode_data` catalog, prioritizing curated metro anchors and then interleaving cities. Leading zeroes are preserved. This source snapshot is NOT proof of current postal coverage or sufficient business inventory; ZIP searches are provider search hints, not guaranteed geographic exclusivity. Plans exceeding catalog coverage reject rather than inventing ZIPs.
- A database advisory-lock gate reserves account slots and estimated provider credits across processes before network dispatch. It considers the provider balance, active Squid slots, local pending/unknown reservations, per-order funded concurrency and cumulative per-order estimated budget. External/legacy account activity is visible only through the provider balance response; Lobstr's own limits remain authoritative.
- Every child persists its Squid before the chargeable `/runs` request, and its returned run ID afterward. The purchase's latest `lobstrRunId` remains compatible with existing APIs. Child IDs are not exposed as customer-supplied allocation inputs.
- Lobstr slots belong to active Squids, not merely running crawlers. Completed/failed owned Squids are deactivated to release capacity. When a parent completes/refunds while a known child still runs, maintenance requests abort and waits for terminal confirmation before releasing its reservation. Provider charges for already-completed work can still apply.
- An ambiguous paid POST becomes UNKNOWN/NEEDS_REVIEW and is NEVER blindly replayed or released after a parent refund. Operators must reconcile those IDs with Lobstr. An interrupted setup may conservatively need review even if no paid run was made; this favors avoiding duplicate charges over automatic throughput.

## Bulk ingestion and exact settlement

- Completed siblings fetch fixed 100-row export pages concurrently. Each group of at most ten pages (1,000 rows) uses one bounded SERIALIZABLE transaction bulk-selects existing identities and uses `Agent.createMany({ skipDuplicates: true })` for new rows. Normalized email and primary/office phone indexes support cross-process identity predicates; serialization conflicts retry. `skipDuplicates` alone is not sufficient for contact deduplication.
- Within that same transaction, source candidate links and each child cursor/count commit together under the parent lease guard. Closed/invalid places are discarded; existing verified Agent rows are not overwritten. Unique-conflict skipped IDs are never published as candidates.
- Process ALL export pages: provider email exports may contain multiple records per business, so an order target of 100 businesses must not truncate a 300-row email export after 100 rows.
- Failed/empty/underfilled children receive unused backup ZIPs while siblings continue. Backups have at most two generations and are also constrained by the cumulative provider-credit budget. Qualified-inventory exhaustion or budget exhaustion uses the existing atomic full-refund path; no silently partial completion.
- PHONE_ONLY skips SMTP and continues server-side email redaction. VERIFIED_EMAIL requires matching-mailbox SMTP 250/251 evidence and rejects MX-only, catch-all or disposable results. The persistent worker verifies candidates concurrently in bounded batches; Vercel HTTP invocations do not open SMTP sockets. No check is a guarantee against future mailbox changes/bounces.
- As soon as exact eligible inventory exists, the existing transaction allocates precisely the ordered lead count, settles the original credit hold, marks COMPLETED and queues the immutable completion email outbox. Allocation deliberately does not use `skipDuplicates`, and no extra customer debit occurs for backup work. Cleanup and email delivery errors cannot undo committed settlement.

## Cadence, deployment and performance

`apps/web/vercel.json` now schedules `/api/cron/process-orders` every minute. Vercel Pro/Enterprise and production `CRON_SECRET` are required; source configuration alone does not activate a deployed schedule. The persistent worker's five-second progress cadence is the fast path and provides SMTP capability; cron and owner-only Vault sync are bounded recovery backstops.

The 500–5,000 leads in 2–5 minutes objective is **unbenchmarked**, not guaranteed. It depends on purchased Lobstr slots, actual Google Maps yield, email verification latency, deduplication and available provider credits. A free one-slot account cannot deliver fifty-slot parallelism. Benchmark both tiers with a controlled paid rollout, report actual distinct eligible leads/minute and provider credits/lead, and tune only within the configured budgets. Automated tests mock provider operations and do not start paid live scrapes or send customer emails.

## Shared registry and scale safeguards

Import helpers from `@fine-leads/utils/territories/us-zip-codes`, not the client utility barrel. `getZipCodesForState` returns defensive copies; `getNextAvailableZips` excludes used ZIPs without wraparound and rejects invalid counts. The source includes 42,366 postal entries across all 50 states plus DC, with complete source city groupings and curated primary metro anchors; it is not a live USPS feed or an official Census metro boundary dataset.

ZIP exhaustion is tracked per parent order through its persisted child rows, parent lease and unique `(jobId, zipCode)` index. Helpers alone do not reserve ZIPs; separate customers can legitimately search the same territory. Account capacity is shared globally via the advisory-lock reservation ledger. Each wave now claims child statuses and creates reservations in two bulk writes instead of a sequential mutation per child. Existing persisted plans retain their previous limits; newly configured plans can request up to 50, subject to provider capacity and budgets. SMTP concurrency remains independently bounded at 10; 50 scraper slots do not imply 50 simultaneous SMTP sockets.

Ingestion flushes only ten completed pages at a time, committing candidate/cursor progress per transaction. If the invocation budget ends, unflushed child cursors remain unchanged and resume on the next invocation. Do not raise the ingestion row cap just because cloud concurrency is 50.
